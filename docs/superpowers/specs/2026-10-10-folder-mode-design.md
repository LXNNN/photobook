# 电子相册 · 文件夹模式设计文档

> 日期：2026-10-10
> 状态：已按审阅反馈修订（v2），待最终确认
> 范围：只含「文件夹模式」核心。第一层数据护栏（配额预检、用量显示、孤儿照片清理）与 PWA 均不在本期，另行设计。
> 前置：可行性验证（spike，`src/pages/FolderProbe.tsx`）全部通过，验证结论见下。
> 修订记录：v2 —— 按审阅反馈改为「一本相册一个文件夹（自包含）」+「删除相册默认连同磁盘数据一起删除（删除前确认）」。

## 一、背景与目标

网站之后要分享给其他人用。现状是：所有数据存在浏览器 IndexedDB 里，用户会担心两件事——**数据被清掉**（清浏览器数据、系统回收空间）和**找不到数据**（换浏览器/换电脑就什么也看不到）。同时浏览器配额有限，照片多了会顶到上限。

文件夹模式要解决的问题：把**照片原图和相册数据以普通文件的形式存到用户自己选的电脑文件夹里**。之后：

- 清浏览器数据、换浏览器、换电脑——照片和相册都不会丢，重新连接文件夹就全回来（已实测）
- 磁盘有多大就能存多少，不再受浏览器配额限制
- 照片就是文件夹里一张张普通的图片文件，不依赖这个网站也能打开

### spike 验证结论（2026-10-10 实测通过）

1. 照片写进所选文件夹后，**清掉浏览器里的授权记录，重新指认同一个文件夹，数据全回来**（数据在磁盘、不在浏览器的实证）
2. 在授权框选「每次访问时允许」后，**完全关闭浏览器再打开 = 自动连接、无弹框**（Chrome 122+ 持久权限机制）
3. **换另一个浏览器**打开同一网址、重新选择同一个文件夹，照片和相册全回来
4. 关键机制（实现时直接复用）：授权记在「origin + 该文件夹」上；授权仍有效时重选同一个文件夹不弹框；三选一授权框（仅这次允许 / 每次访问时允许 / 不允许）出现在：① 首次选一个全新文件夹时；② 浏览器重启后对记录里的句柄调 `requestPermission()`（即点「重新连接」）时。`requestPermission()` 必须在用户手势（点击）里调用。

### 目标用户的取舍（已确认）

- 排除手机端；文件夹模式只承诺 **Chromium 桌面端（Chrome / Edge）**，Windows 上 Edge 预装，相册书人群覆盖足够
- Firefox / Safari 优雅回退到现状（IndexedDB 模式），功能不受影响
- 核心价值主张：**数据看得见、找得到、不会被浏览器弄丢**

## 二、核心模型

**浏览器从"仓库"降级成"工作台"。** 文件夹是本体，浏览器是操作台。

数据分三份看：

| 数据 | 存在哪 | 丢了怎么办 |
|---|---|---|
| 照片原图 | 用户文件夹（普通文件，每本相册一个文件夹） | 浏览器没有任何机制能自动删它；只有主动删除（网站上删相册、或自己删文件夹）才会丢，靠备份兜底 |
| 相册排版 + 模板 | 用户文件夹（json 文件，每本相册一份 + 全局模板一份）；浏览器里留一份缓存 | 以文件夹为准，两边合并 |
| 浏览器侧：连接授权、缩略图 | 浏览器 IndexedDB | 授权丢了点一下重连/重选；缩略图丢了可从磁盘照片重新生成 |

## 三、范围

**做：**

- 文件夹的目录结构、连接与授权管理
- 首次启用；已有相册的迁移（先写盘验证、才清浏览器大图）
- 连接状态 UI（首页横幅、空书架入口、编辑器提示）
- 断连 / 文件夹丢失 / 换浏览器换电脑的恢复路径
- **自定义模板随文件夹同步**（用户在编辑器新增/修改/删除的自定义模板，写进文件夹；换浏览器也能显示）
- 备份模块对接（导出格式不变，图片从文件夹读；导入写回文件夹）
- 删除相册：默认连同该相册的文件夹一起删除（删除前确认）

**不做（本期）：**

- 手机端、Firefox/Safari 的文件夹模式
- PWA / 安装到桌面
- 第一层数据护栏（配额预检、用量显示、孤儿照片清理）
- 「完全离线可用」的编辑模式——启动时未连接不能进入编辑（§5.3）；只有编辑中途断连才允许带暂存继续（§6.6）
- 多设备同时编辑同一个文件夹（顺序换着用没问题）

## 四、磁盘目录结构

```
<用户选的文件夹>\
└─ photo-book\                 ← 应用自建子目录，用户原文件夹里其他内容一概不受影响
   ├─ 我的模板.json             ← 全部自定义模板（与备份包中同名文件同构）
   ├─ 先看我-说明.txt           ← 给用户看的大白话说明（内容见 §9.3）
   ├─ 蜜月旅行\                 ← 一本相册 = 一个文件夹，自包含
   │   ├─ 相册数据.json          ← 这本相册的排版 + 它的照片清单
   │   └─ 照片\0001.jpg、0002.jpg…  ← 这本相册的照片原文件
   └─ 宝宝周岁\
       ├─ 相册数据.json
       └─ 照片\…
```

规则：

- **一本相册一个文件夹**：照片和排版数据都放在这本相册自己的文件夹里，整个文件夹拷走就能独立打开——和备份 zip 解开的形态完全一致。
- **相册文件夹名** = 相册名清洗非法字符后（沿用备份模块 `safeFolderName` 的规则，含撞名顺延「(2)」；已用名集合取 `photo-book\` 下现有的子文件夹）。名字在相册创建时定下：网站里改名**不会**同步改文件夹名（改一次要搬所有照片，太重）；网站认相册靠 `相册数据.json` 里的相册 id，不靠文件夹名——用户手动改文件夹名也不影响识别。
- **照片按相册各自编号**：迁移时按 `createdAt` 排序（同时间按 id）在本书的 `照片\` 里依次编号，稳定可重跑；之后新上传的取"该相册现有最大编号 + 1"（上传时扫该相册的 `照片\` 取最大值，不存计数器，永不失配）。扩展名沿用原类型（.jpg/.png/.webp 等，与备份模块 `extFor` 一致）。
- **共用照片各存一份**：同一张照片被两本相册用到时，在每本相册的文件夹里各存一份——换来每本文件夹自包含、删一本不影响另一本；代价是占两份空间。
- **写入 / 删除边界**：只在 `photo-book\` 子目录内部读写；子目录外的任何文件不读、不改、不删（唯一的删除动作见 §6.10）。
- `先看我-说明.txt` 以 **UTF-8 带 BOM** 写入（Windows 记事本识别中文需要 BOM）。
- `我的模板.json` 的结构与备份包里的一致（`formatVersion` + `templates` 数组），导出/导入的解析代码直接复用。

## 五、连接状态机与界面

### 5.1 状态定义

| 状态 | 含义 | 怎么到达 |
|---|---|---|
| `unsupported` | 浏览器不支持（无 `showDirectoryPicker`） | 启动检测 |
| `off` | 支持，但用户还没启用文件夹模式 | 启动时 IndexedDB 里没有句柄记录 |
| `connected` | 已连接，正常读写 | 启动时 `queryPermission` 为 granted；或用户完成连接操作 |
| `needs-reconnect` | 有记录但权限待确认（浏览器重启后等） | `queryPermission` 为 prompt / denied |
| `folder-missing` | 权限在手，但文件夹/相册数据读不到（被移动/改名/盘没插/被删） | 连接动作中读文件抛 `NotFoundError` 时 |

状态是**模块级可订阅对象**（`useSyncExternalStore`，同 `templates` 模块的既有模式），并带一个 `dataVersion` 计数——连接/合并完成后 +1，页面据此刷新书架。

### 5.2 首页横幅（ProjectList 顶部）

Chromium（supported）时，替换现在那条琥珀色备份提醒为文件夹状态横幅，按状态显示（文案见 §9.1）：

- `off`：推荐启用 + 「选择文件夹」按钮
- `connected`：安静的状态条「照片已存到电脑文件夹：{文件夹名}」+「重新选择」
- `needs-reconnect`：「点一下重新连接」按钮（在弹出框里选「每次访问时允许」）
- `folder-missing`：引导「重新指认文件夹」
- `unsupported`：保持现在的琥珀色备份提醒原文案不变

### 5.3 空书架入口与操作守卫

- 书架为空且 supported：空状态里加「连接已有的相册文件夹」入口（换电脑/换浏览器恢复的入口）+ 保留现有创建按钮
- 守卫 `ensureFolderReady()`：folder 模式已启用但未连接时，点「创建相册」「编辑」「预览」「删除」「导出备份」「导入备份」「上传」等动作 → 不进入，先弹「需要重新连接」引导（点一下即可；删除也要先连接，因为要同时清理磁盘数据）。`off` / `unsupported` 状态一切如旧，不加任何拦截

## 六、关键流程

### 6.1 首次启用（书架为空）

点「选择文件夹」→ `showDirectoryPicker({ mode: 'readwrite', id: 'photo-book' })` → 创建 `photo-book\` 结构（写入 `我的模板.json` + 说明文件；相册文件夹在创建相册时生成）→ 状态 `connected`、置「迁移完成」标志。以后上传的照片直接写进对应相册的文件夹。

### 6.2 迁移（书架已有相册）

选完文件夹后如果本机已有相册 → 弹窗确认（文案 §9.2）→ 开始迁移（迁移完成前保持「未迁移」标志）：

1. 逐本相册建文件夹，按 §4 编号规则给这本书的照片分配文件名（内存里定好）
2. 逐张：写文件 → 重新读出比对大小 → 通过才在内存清单里落这条记录（已存在且大小一致的跳过，**可中断、可重跑、幂等**）
3. 一本书的照片全部通过后：写它的 `相册数据.json` → 重新读出并 `JSON.parse` 校验
4. 全部相册完成后：写 `我的模板.json` + 说明文件 → 校验
5. **都验证无误之后**，才清理浏览器里的大图：逐条把 IndexedDB `images` 记录里的 `blob` 去掉（保留缩略图与元数据）
6. 置「迁移完成」标志、状态 `connected`，完成提示

任何一步失败/关页面：磁盘上的东西不动，浏览器里的数据也一个没删（第 5 步没到就什么都没清），下次重来接着搬。

如果选的文件夹里**已经有**相册数据（换电脑场景）→ 不跑上面的迁移，走 §6.5 的连接合并；迁移与合并本身共用同一套"逐本比对、缺什么补什么"的规则，不会互相打架。

### 6.3 启动自动连接

`main.tsx` 中、React 渲染前：`await initFolderMode()`（时机见 §7.6）：

- 无句柄记录 → `off`
- `queryPermission` = granted → 读 `photo-book\` 下各相册文件夹的 `相册数据.json` → 按 §6.5 合并 → `connected`（静默，不弹任何框；书架有被动变化时用轻提示告知，如「『XX』的文件夹不在文件夹里了，已从书架移除」）
- 读不到 `photo-book\` 子目录 → `folder-missing`（相册数据不见了：可能被删、被换过，引导重新指认）
- prompt / denied → `needs-reconnect`（横幅待命，等用户点）
- 读目录抛 `NotFoundError` → `folder-missing`

### 6.4 重新连接

用户点「重新连接」→ 在点击手势里 `requestPermission({ mode: 'readwrite' })` → 弹出三选一授权框 → 选「每次访问时允许」（横幅文案这样引导；选「仅这次允许」也放行，只是下次重启还要再点一次）→ 通过后立即执行 §6.3 的连接逻辑；被拒则留在原状态并提示。

### 6.5 连接已有文件夹 / 重新选择（合并规则）

凡"绑定到一个文件夹"（换电脑、换浏览器、重新选择、重新指认），统一走同一套合并：

- **相册**：按 id 合并。
  - 同 id 两边都有 → 取 `updatedAt` 新的那本（新的在本地 → 补写文件夹；新的在文件夹 → 载入本地）
  - 仅文件夹有 → 载入书架
  - 仅本地有 → 分两种：
    - 本机还没把书架搬进这个文件夹（「迁移完成」标志为假，或连的是另一个文件夹）→ 补写进文件夹
    - 已经搬过（日常重连同一个文件夹）→ 判定为磁盘上的相册文件夹被手动删掉了 → 从书架移除，轻提示
- **照片**：按 id 合并，以相册文件夹里的文件为准；缺文件的 → 对应元素渲染占位（§10）。合并后重建「图片 id → 文件位置」内存索引（同一 id 在多本相册里各有文件时，任取其一读取，内容相同）
- **自定义模板**：见 §6.8
- **缩略图**：本地缺缩略图的照片，后台从磁盘照片逐张重新生成回填（先占位后替换，不阻塞界面）
- 指认到的文件夹里没有 `photo-book\` 数据 → 先建好结构，再按上面的规则处理（视为未迁移，本机相册补写进去）
- 合并完成后 `dataVersion + 1`，书架刷新
- 用户主动发起、且两边都有内容时先弹确认（文案 §9.2）；启动静默连接不弹框

「迁移完成」标志存在浏览器里（与句柄记录一起，§7.4）；判断"是不是同一个文件夹"用 `isSameEntry` 比对已记录的句柄。

### 6.6 日常保存与中途断连

- 相册排版改动：沿用现有 3 秒防抖自动保存节奏 → 同时写 IndexedDB（现状不变）和**该相册自己的** `相册数据.json`（原子写，见 §7.5）；手动保存、页面隐藏（`visibilitychange`）时补一次
- **写盘失败**（句柄失效等）：状态转 `needs-reconnect`，记下"有改动没写进文件夹"的标记；编辑可继续（改动始终先落浏览器），界面给提示（§9.4）；重连成功后**自动把本地较新的版本补写上去**
- **启动时未连接**：不进入编辑（见 §5.3 守卫）。中途断连与启动未连接是两种处理，故意的：启动时照片根本读不出来，进去也没意义；中途断连时手里有缓存、改动有地方落，就允许继续
- **中途断连期间新增/替换的照片**：先带 blob 暂存在 IndexedDB + 记「待补写」；重连后写入对应相册文件夹、校验通过再清掉浏览器里的这份 blob

### 6.7 上传与替换照片

上传（CreateWizard）、编辑器内上传、替换图片（PropertyPanel）统一走资产仓库（§7.2）：处理后的 blob **写进当前相册文件夹的 `照片\`（该相册的新编号）** → 元数据 + 缩略图进 IndexedDB → 该相册清单与图片索引同步更新。从入口发起时若未连接，被守卫拦下先重连（§5.3）；编辑器**中途**断连后的上传/替换走 §6.6 的暂存路径。

### 6.8 自定义模板同步（★ 用户补充要求）

**要求：用户在编辑器里新增的自定义模板，必须写进本地文件夹；换浏览器/换电脑连接文件夹后，自己加的模板都能显示。**

- 写：模板库的持久化通道（`utils/templateLibrary.ts` 的 `persistTemplate` / `deleteTemplateFromLibrary`）在写完 IndexedDB 后，调度一次 `我的模板.json` 写盘（短防抖即可，模板操作低频）
- 读：连接文件夹时读 `我的模板.json`，按备份模块 `importTemplates` 的既有合并规则并入模板库：
  - id 相同 = 同一模板 → 以文件夹版本为准
  - 仅本地有 → **补写进文件夹**（保证刚新增的不丢——这是本节的硬要求）
  - 仅文件夹有 → 载入本地
  - 仅名字撞、id 不同 → 两个都留，后并入的改名「（导入）」（实现时可把 `importTemplates` 提取为文件夹与备份共用的工具函数）
- 迁移时：把本机现有自定义模板一并写进 `我的模板.json`
- 断连期间产生的模板改动记入"待补写"，重连后先向上补写（同 id 覆盖文件夹）再合并
- 模板文件始终在 `photo-book\` 根目录（全局一份），不随相册文件夹走
- 已知边界（§11）：另一台机器上删除过的自定义模板，可能被某台"手里还有旧副本"的浏览器在下次重连时补写回来一次——可再次删除，不丢数据的方向优先

### 6.9 备份导出 / 导入

- **导出**：zip 结构、文件名、合并规则全部不变（一本相册一个文件夹、自包含）——导出就是把各相册文件夹打包。只改图片来源：从资产仓库取（已启用 → 从文件夹读；未启用 → 从 IndexedDB 读）
- **导入**：解析与冲突规则不变；每本相册的照片写进它自己的文件夹（新建文件夹或并入已存在的），清单与索引同步更新。未连接时导出/导入按钮都先引导重连（§5.3）
- 说明文件里写明：「有了文件夹之后，最简单、最完整的备份就是把整个 photo-book 文件夹复制到网盘或 U 盘」——每本相册的文件夹也能单独拷走

### 6.10 删除相册（连同磁盘数据）

删除 = **书架记录 + 该相册的整个文件夹一起删**，但必须先经过明确确认（这是网站里唯一会删磁盘文件的地方）：

1. 未连接 → 守卫先引导重连（§5.3）
2. 已连接 → 弹确认框（文案 §9.2）：写明会从电脑文件夹里一并删除、不可恢复
3. 确认后：删该相册文件夹**之前**先重读里面的 `相册数据.json` 核对相册 id 与所删一致，一致才删（整个文件夹递归删除）；然后删书架记录、更新图片索引
4. 个别文件删不掉（被占用等）→ 不中断，删完其余，最后提示「还有 N 个文件没删干净，可以在电脑上手动删除」
5. 文件夹模式未启用 → 维持现状（原生确认框，无磁盘动作）

用户自己删文件夹同样成立：某本相册的文件夹被手动删掉后，下次连接/启动时该相册从书架同步移除（§6.5）。

## 七、技术实现

### 7.1 新模块与依赖方向

| 模块 | 职责 |
|---|---|
| `src/utils/folderMode.ts` | 连接层：支持检测、句柄存取（IndexedDB `settings`）、`queryPermission`/`requestPermission` 封装、选文件夹/重连、文件原语（读/写/列目录/原子写/递归删除）、状态订阅对象 |
| `src/utils/folderLibrary.ts` | 书架层：各相册文件夹的 `相册数据.json` 读写、合并、迁移、说明文件、`我的模板.json` 读写、待补写队列、`initFolderMode()` |
| `src/utils/assetStore.ts` | 资产仓库：读图/存图的统一入口 + 内存缓存 + 图片索引（见 7.2） |
| `src/components/FolderBanner.tsx` | 首页横幅四态 |

依赖方向（防循环引用）：

```
storage.ts（最底层，不许 import 上面任何新模块）
   ↑
folderMode.ts ← folderLibrary.ts ← assetStore.ts ← 各页面 / backup.ts
                                    ↑
                       templateLibrary.ts 挂文件夹镜像（拿到"写模板 json"的函数）
```

`templates/` 目录依然不许反向 import storage 或新模块；模板落盘继续只走 `templateLibrary.ts` 这个既有通道；它通过注册的回调钩子通知文件夹层写盘，不直接 import folderLibrary（模板合并逻辑放在 folderLibrary 侧），避免循环引用。

### 7.2 资产仓库（读图/存图收口）

现在 `getImageAsset`/`saveImageAsset` 散在 6 个文件里（CreateWizard、Editor、ProjectList、Viewer、PageThumbnail、PropertyPanel、backup）。统一改为从 `assetStore.ts` 进出：

```ts
// 渲染用全图：已启用 → 读文件夹（带小容量 LRU 内存缓存，避免同屏反复读盘）；未启用 → IndexedDB（现状）
getImageAsset(id): Promise<ImageAsset | undefined>
// 只要缩略图/元数据（封面、面板小预览）：永远读 IndexedDB，绝不触发读盘
getImageMeta(id): Promise<{ thumbnail; width; height } | undefined>
// 上传/替换：已启用 → 写进该相册文件夹 + 更新清单与索引 + 元数据进 IDB；未启用 → IDB（现状）
saveImageAsset(projectId, asset): Promise<void>
```

- **图片索引**：连接/合并后扫描各相册文件夹的清单，建立「图片 id → 文件位置」内存索引（同一 id 可能在多本相册里各有一份，任取其一读取）；上传、删除相册时同步维护。某处读不到就试下一处，都失败则渲染占位
- `drawPageContent` 及全部渲染代码**一份不改**：仓库返回的仍是带 `blob` 的 `ImageAsset`，坐标/画法完全不动
- 封面（ProjectList）、PropertyPanel 小预览改走 `getImageMeta`（沿用"封面用缩略图"的既有性能结论）；PageThumbnail 暂维持读全图（与主画布逐字一致的既有取舍），给实现留一个观察项：大相册侧栏慢的话再让页面缩略图走缩略图源
- LRU 容量取小（几十张级别），目的只有一个：一屏渲染/翻页/缩放时同一张图不反复读盘

### 7.3 清单格式（每本相册自己的 `相册数据.json`）

```ts
interface AlbumFile {            // 相册文件夹\相册数据.json
  app: 'photo-book';
  formatVersion: 1;
  updatedAt: number;
  project: Project;              // 这本相册（与 IndexedDB 中结构一致；id 是识别相册的钥匙）
  images: AlbumImageRecord[];    // 这本相册用到的照片
}

interface AlbumImageRecord {
  id: string;
  file: string;                  // 相对该相册文件夹，如 "照片/0001.jpg"
  type: string;
  width: number;
  height: number;
  size: number;
  createdAt: number;
  // 注意：不含缩略图。缩略图属浏览器缓存，缺了可从磁盘照片重新生成
}
```

- 与备份包里每本相册的 bundle 同构（`file` 相对相册文件夹），导出/导入的解析代码直接复用
- `我的模板.json`：`{ formatVersion: 1, updatedAt: number, templates: [...] }`（与备份包同构，放 `photo-book\` 根目录）

### 7.4 IndexedDB 升级（只加不改）

`photo-book-db` 版本 3 → 4，`upgrade` 里**只新增**一个 store：`settings`（keyPath `key`），存 `{ key: 'folderHandle', value: FileSystemDirectoryHandle }` 与 `{ key: 'folderMigrated', value: boolean }`（本机是否已把书架搬进当前记录的文件夹；换文件夹后重算）。现有 4 个 store 一律不动。迁移后 `images` 记录形如 `{ id, thumbnail, width, height, size, createdAt }`（无 `blob`），仅在文件夹模式清理步骤之后出现；类型上把存储记录与渲染资产分开（存储记录 `blob` 可选，仓库出口的 `ImageAsset.blob` 保持必填）。

### 7.5 原子写与校验

- 所有文件写入：`createWritable()` → `write()` → `close()`（close 即原子替换，spike 已用此法）
- 相册清单写后抽查：重新读出 + `JSON.parse` 成功才算数
- 照片写后校验：`getFile().size` 与源一致
- 清单写入防抖 3 秒（对齐编辑器的自动保存节奏），模板 json 短防抖；页面隐藏时补写一次
- 删除相册文件夹：逐文件 `removeEntry` 再删文件夹本身；个别失败不中断，最后统一汇报（§6.10）

### 7.6 启动顺序（main.tsx）

```
await initTemplateLibrary();   // 现状：先载入模板库
await initFolderMode();        // 新增：连接/合并（内部含模板文件夹合并）
createRoot(...).render(...)
```

`initFolderMode` 全程 try/catch：任何失败只影响状态与横幅，**绝不阻塞应用启动**。

### 7.7 涉及改动的文件

- 新增：`folderMode.ts`、`folderLibrary.ts`、`assetStore.ts`、`FolderBanner.tsx`
- 修改：`main.tsx`（启动顺序）、`ProjectList.tsx`（横幅/空状态入口/守卫/封面走 getImageMeta/删除确认框）、`Editor.tsx`（资源加载与上传走仓库；顶部提示条）、`CreateWizard.tsx`、`Viewer.tsx`、`PageThumbnail.tsx`、`PropertyPanel.tsx`（替换与预览）、`backup.ts`（图片进出走仓库）、`templateLibrary.ts`（文件夹镜像钩子）、`storage.ts`（v4 升级 + `settings` 读写 + `getImageMeta` 支持）、`types/index.ts`（存储记录类型）
- 实现收尾时：删除 `FolderProbe.tsx` 与 `App.tsx` 里的 `/folder-probe` 路由（spike 是一次性代码）

## 八、数据安全规则（红线）

1. 只读/写/删 `photo-book\` 子目录内部；用户文件夹里的其他任何文件不读不改不删
2. 迁移第 5 步（清理浏览器大图）**必须**在所有写盘校验通过之后才执行；任何失败就停，浏览器数据一个不删
3. 网站删磁盘文件**只有一处**：用户在网站里确认删除某本相册时，连同它的文件夹删掉——删前核对 `相册数据.json` 里的相册 id、删不干净就停手提示；`photo-book\` 之外的任何东西永远不删。除此之外网站永不删磁盘文件
4. IndexedDB 升级只加不改；现有 4 个 store 的数据一个字节不动
5. 未连接时一切写盘动作停止（靠守卫拦下），绝不做"先写浏览器里等等看"的假承诺——改动要么写进文件夹并验证，要么明确告诉用户在浏览器里暂存
6. 授权被拒 / 文件夹丢失 / 写失败：只降级提示 + 引导重连，不丢任何一份数据

## 十、错误与边界逐场景

| 场景 | 表现 | 处理 |
|---|---|---|
| 浏览器不支持 FSA | `unsupported` | 横幅维持现状；全部功能照旧（IndexedDB） |
| 用户取消选择文件夹 | 无变化 | 什么都不发生 |
| 用户拒绝授权 | 停在原状态 | 提示可再试（§9.4）；连续被拒后 Chrome 会静默降级，届时提示换一个文件夹 |
| 浏览器重启后权限降级 | `needs-reconnect` | 横幅 + 一键重连（spike 已实测） |
| 文件夹被移动/改名 | 连接时 `NotFoundError` | `folder-missing`；重新指认后走合并（按 id，不会重复建文件） |
| U 盘没插 | 同上 | 同上；插好后重试 |
| `photo-book\` 子目录被删 | 连接时发现读不到 | `folder-missing`（当作"相册数据不见了"，不静默重建、不静默清书架）；指认后按 §6.5 合并 |
| 文件夹被整个删除，用户指认了一个空文件夹 | 指认后建好结构 | 提示「照片原图不在这里」：能从浏览器里拿到的（排版、尚未清理的照片）先写进新文件夹；拿不到的照片渲染占位，用备份 zip 找回 |
| 某本相册的 `相册数据.json` 损坏/被手改坏 | 解析失败 | 只跳过这一本、不覆盖：提示「『XX』的相册数据读取失败」，保留现场；其他相册不受影响 |
| 用户手动删掉某本相册的文件夹 | 连接/启动时发现 | 从书架移除该相册并轻提示（§6.5） |
| 用户手动改相册文件夹名 | 无感知 | 无影响：按数据里的相册 id 识别，重连后重新扫描照样找到 |
| 迁移中途关页面 | 下次启动检测到未完成 | 重新提示接着搬（幂等跳过已写好的） |
| 编辑中途文件夹被拔走 | 写盘失败 | 状态转 `needs-reconnect` + 编辑器提示；改动落浏览器；重连后自动补写 |
| 删除相册时个别文件删不掉 | 继续删其余 + 最后提示 | 提示手动清理（§9.4）；书架记录已删 |
| 同一文件夹两台机器同时用 | 后保存的覆盖先保存的 | 已知限制（§11），文案不承诺并发 |
| 导入的备份里照片 id 已存在 | 按现有规则跳过重复 | 现状逻辑不变 |

## 十一、已知限制（明说）

1. 同一文件夹同一时间只在一台机器/一个浏览器里用；换设备前先保存并关掉那边（顺序使用完全没问题）
2. 另一台机器删除过的自定义模板，可能被持有旧副本的浏览器重连时补写回来一次（保护"新增不丢"的代价，可再删）
3. 内置模板的删除记录（墓碑）不进文件夹（与备份包行为一致）；换浏览器后内置模板恢复默认显示
4. 隐身模式下授权与数据都是临时的，不做特别提示
5. PageThumbnail 读全图维持现状（性能观察项）
6. 照片文件名为各自相册内的顺序编号，不是原始文件名；对应关系都在该相册的 `相册数据.json` 里
7. 同一张照片被两本相册用到时，磁盘上会存两份（每本相册的文件夹各一份）
8. 网站里改相册名后，磁盘文件夹名保持创建时的；不影响识别（按数据认相册）
9. 把连接换到"另一个文件夹"时，本机书架上有、文件夹里没有的相册会被补写过去（安全方向：宁可多写不丢）

6. 编辑器里新增自定义模板 → `我的模板.json` 立即出现该模板
7. 文件夹改名 → 提示找不到 → 指认回来数据无损
8. 编辑器开着拔走 U 盘/挪走文件夹 → 提示出现、改动不丢 → 恢复后自动写入
9. 删除相册 → 确认框写明会删磁盘 → 确认后书架和文件夹都删掉；**确认文件确实没进回收站**（若进了，说明文件相应放宽）；取消则什么都不发生

12. 共用照片：同一备份导入两次产生两本共用照片的相册 → 两个文件夹各有一份；删掉其中一本，另一本的照片还在
13. 导出备份 → zip 结构与现状一致 → 在另一个浏览器导入 → 照片写进对应相册文件夹
14. Firefox/Safari 打开 → 一切与现状相同
15. 连续整轮操作后 IndexedDB 里 images 记录确认无 blob、缩略图在
